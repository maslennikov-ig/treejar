# Noor: независимое предложение по исправлению и выбору модели

Статус: собственная версия до сравнения с внешним заключением. Это не финальная
спецификация и пока не меняет Beads.

## Решение

Сначала исправить детерминированную логику Noor и подсчёт качества. Затем на
шести самых трудных сценариях сравнить четыре core-chat модели. Полный локальный
и production-прогон выполнять только для победителя. Внешний баг webhook-статусов
Wazzup оставить отдельным заблокированным критерием: он не должен искажать выбор
модели, но до исправления провайдером не считается доказанной доставка
`delivered/read`.

## Почему текущий результат не прошёл

Финальный прогон 3 августа дал **18,4/30** при требовании не ниже **24/30**.
Основные причины находятся не только в модели:

- каталог, Zoho и сохранённое состояние иногда собирают окончательный ответ без
  участия модели;
- планировщик оптимизирует дешёвое покрытие мест и может смешивать несвязанные
  товары вместо цельного решения;
- отказ от КП ошибочно превращается в состояние `quotation on hold`;
- продолжение запроса после name gate доверено текстовой инструкции модели и не
  имеет строгого постусловия;
- типизированное состояние иногда уже содержит ложные факты: бюджет попадает в
  адрес, компания конфликтует с типом клиента, а `sales_stage` и `active_flow`
  остаются на старом этапе;
- оценщик определяет применимость правил по английским словам и старому этапу
  диалога, а полностью неприменимые блоки превращает в нули вместо корректной
  нормализации.

Следовательно, простая замена модели не исправит S04/S05/S08/S10 и сделает
сравнение нечестным.

## Исправления до сравнения моделей

### 1. Каталог и коммерческие факты — `tj-ee5f.7`

- Ввести общий `CatalogDecision` для model-owned и статических маршрутов:
  требования, совместимые строки, покрытие мест, бюджетная арифметика, снимок
  остатков, неизвестные факты и требуемый клиентом вывод/рекомендация.
- Каталог является источником цены и описания, Zoho — текущего остатка; у факта
  есть `source` и `as_of`.
- Не показывать сохранённый каталоговый остаток как текущий, если запрошен или
  доступен Zoho readback.
- Изменить цель планировщика: сначала обязательные ограничения и полное
  покрытие, затем совместимость решения, минимальное число разных SKU, бюджет
  и релевантность; минимальная цена — только после них.
- По умолчанию давать один совместимый SKU на семейство. Смешивать позиции
  только когда цельный вариант невозможен и такое сочетание честно объяснено.
- Строить сравнение и рекомендацию по подтверждённым фактам, а неизвестные
  акустику, размеры и свойства явно оставлять неизвестными.
- После name gate исполнять сохранённый типизированный intent через тот же
  маршрут и проверять постусловие: исходная задача продолжена, повторного
  вопроса «что вам нужно?» нет.

### 2. Состояние КП — `tj-ee5f.8`

- Хранить жизненный цикл:
  `consultation → quote_offered → quote_requested → collecting_details → creating → created`.
- Согласие хранить отдельно как `quote_consent = absent | declined | opted_in`;
  отказ не является этапом или паузой.
- Новые поля писать версионированно, старое `quote_on_hold` только читать для
  обратной совместимости и однозначно преобразовывать.
- Удалить fallback, который принудительно включает `quote_on_hold`, когда
  предложение КП запрещено.
- После явного отказа отвечать, что КП не готовится, пока клиент сам не попросит
  позже; не собирать количество и реквизиты.
- Вопросы о доставке, исправление количества, возражение и точный SKU проверять
  до quote collection.
- Перед маршрутизацией выполнять одну каноническую сверку состояния: бюджет не
  может быть адресом, компания не должна превращать клиента в `individual`, а
  stage, active flow и slots обязаны описывать один и тот же ход диалога.

### 3. Честный оценщик — `tj-ee5f.12`

- Определять применимость каждого правила по типизированным событиям диалога,
  каталога и КП, а не по английским ключевым словам.
- Поддержать EN/AR/RU и многоходовые исправления без языковых списков фраз в
  production-коде.
- Исключать неприменимые веса и нормализовать оставшиеся на шкалу 0–30.
- Зафиксировать небольшие human-labelled fixtures: name gate, Arabic catalog,
  exact SKU + no quote, no-match, objection, quote opt-in.
- Не менять одновременно core-chat модель и модель-судью.

## Четыре кандидата

Точные OpenRouter ID, проверяемые ещё раз бесплатным metadata-preflight перед
платными вызовами:

| Кандидат | ID |
|---|---|
| Текущий baseline | `z-ai/glm-5.2` |
| DeepSeek Flash | `deepseek/deepseek-v4-flash` |
| GPT Luna | `openai/gpt-5.6-luna` |
| Xiaomi MiMo | `xiaomi/mimo-v2.5-pro` |

Не использовать alias `latest` и не подменять отсутствующую модель похожей.

## Минимальная конфигурация сравнения

- Закрепить first-party provider для каждой модели через `provider.only`,
  `allow_fallbacks=false`, `require_parameters=true`.
- Общий основной режим: `reasoning.enabled=false`, `tool_choice=auto`, без
  `temperature`, `top_p`, penalties и `stop`; одинаковый разумный лимит ответа.
- Не требовать строгий JSON Schema там, где first-party endpoint его не
  подтверждает. Инструменты проверять через обычные tool calls и локальную
  валидацию аргументов.
- Если ни одна модель не проходит hard gates, повторить только две лучшие на
  двух наиболее различающих сценариях с reasoning, поддерживаемым конкретным
  endpoint. Это отдельный конфигурационный раунд, а не скрытая настройка.
- Сохранять фактические endpoint, параметры, токены, цену и latency. Цена из
  generation metadata важнее рекламной цены карточки.

Такой режим сокращает reasoning-токены и устраняет конфаундер: сейчас Noor
отключает reasoning только для DeepSeek Flash, а у остальных кандидатов он
может включаться по умолчанию.

## Короткий сложный тест

Расширить существующий `scripts/model_battle.py`, а не создавать новый harness.
Добавить профиль `remediation-hard` с многоходовыми fixtures. Точные фразы
хранятся только в tests/evidence.

1. S01: EN name gate, цельный mixed package и соблюдение бюджета.
2. S02: Arabic discovery, каталог и уместный tool use без эскалации.
3. S03: private workstation и повторная проверка stock без противоречий.
4. S04: comparison с неизвестными acoustic/footprint и обязательной рекомендацией.
5. S05: связное 12-seat решение, lumbar, бюджет, cross-sell и отказ от КП.
6. S08: исправление 2→3, прерывающий вопрос, память и строгий no-quote.

Каждый кейс обязан попадать в model-owned путь. Если ответ целиком формирует
детерминированный renderer, это regression gate исправления, а не балл модели.
Модели получают одинаковые типизированные tool results и снимок product prompt.

Первый раунд: **4 модели × 6 кейсов × 1 попытка = 24 задания**. Семантические
ошибки не ретраить. Разрешить один повтор только при 429/5xx/transport timeout;
обе попытки учитывать в стоимости и latency. При практической ничьей — максимум
четыре дополнительных задания: две лучшие модели на двух наиболее различающих
кейсах.

До платного запуска получить provider upper estimate и зарезервировать не более
`1,25 × estimate` на кандидата; неизвестная цена блокирует его запуск. Судейские
вызовы считать отдельно.

## Выбор победителя

Сначала обязательные hard gates:

- нет выдуманных фактов и критической ошибки инструментов;
- не потерян intent, язык, количество или отказ от КП;
- нет нежелательного КП/CRM side effect;
- каждый кейс не ниже 20/30, среднее не ниже 24/30;
- все обязательные структурные assertions пройдены.

Среди прошедших кандидатов сначала сравнить средний слепой балл /30, затем
процент объективных assertions и надёжность tool calls. Фактические стоимость и
p95 latency — tie-breakers, а не способ компенсировать худшее качество.

Если никто не прошёл hard gates, результат — `no_safe_replacement`; выбирать
«лучшего из плохих» нельзя. Разница менее 1,0 балла считается ничьей: повторить
только две лучшие модели на двух наиболее различающих кейсах. Если ничья
сохранилась, оставить текущий baseline, если challenger не дал измеримого
выигрыша в критических assertions.

## Полная проверка победителя

После выбора заменить только конфигурационный `openrouter_model_main`; ID модели
не хардкодить в product-ветках. Затем выполнить один release gate:

```text
uv run ruff check src/ tests/
uv run ruff format --check src/ tests/
uv run mypy src/
uv run pytest tests/ -v --tb=short
scripts/orchestration/run_process_verification.sh
```

После отдельного подтверждения владельца на платные/live/remote действия:

- fresh fetch, non-force push, канонический deploy и readback точного SHA;
- один production S01–S10 прогон победителя;
- provider-originated EN/AR/voice canaries;
- S09: точный Zoho order, PDF, readback и очистка;
- S10: точный CRM readback без КП и очистка;
- каждый текстовый сценарий ≥20/30, среднее ≥24/30, без функциональных FAIL и
  P0/P1.

После смыслового дефекта повторять только затронутый сценарий. Широкий платный
прогон заново не запускать.

## Оркестрация

**Уровень:** complex integration.

**Граница:** один активный implementation stage `tj-ee5f` для исправлений,
выбора модели и winner-only acceptance. `tj-ee5f.5` остаётся отдельной внешней
границей Wazzup.

**Потоки внутри stage:**

- A — `.7`: каталог, факты, планировщик, name-gate postcondition;
- B — `.8`: quote lifecycle/disposition;
- C — `.12`: применимость и нормализация оценщика;
- D — короткий четырёхмодельный battle после A/B/C;
- E — внедрение победителя и полная приёмка после D.

**Scope ledger:** frozen AC-01…AC-30 и digest не менять. A покрывает каталог и
intent, B — consent/refusal, C — доказуемый quality score, D выбирает способ
реализации и не создаёт новый acceptance criterion, E повторно доказывает все
AC. Wazzup terminal delivery остаётся в `.5` как внешний BLOCKED.

**Beads после сравнения с внешним заключением:** переиспользовать `.7`, `.8`,
`.12`; создать `.13` только на sealed focused model battle, заблокированный
`.7/.8/.12`. `.14` на config adoption нужен только при победе challenger.
Winner-only production acceptance остаётся ответственностью `.1`. Новый
umbrella не создавать.

**Следующая стадия:** после принятия финальной спецификации — focused TDD A/B/C,
затем D, затем E. Epic не закрывать, пока `.5` не получит будущий реальный
status webhook или владелец формально не изменит критерий закрытия.
